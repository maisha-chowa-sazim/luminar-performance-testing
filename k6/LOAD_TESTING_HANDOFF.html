This report describes the current local implementation, including changes after commit 0f360be. It is an implementation handoff, not a capacity or release sign-off. No load test was executed to prepare it.

1. Scope and design decisions

The primary load profile runs Merchandiser and Inventory users independently and concurrently. Merchandisers create linked business records; Inventory users receive eligible work orders produced by the same run. Each business VU has a distinct assigned account and reuses its authenticated session.

DecisionImplementation and reason
Independent concurrent rolesTwo ramping-vus scenarios model producers and consumers progressing at different speeds.
Maximum 50 business VUsThe configured role counts must sum to the requested total, which cannot exceed 50.
Work-order approval onlySenior Merchandiser approves each work order and sends it to the supplier before receiving. BOM, costing and purchase-order approvals/submissions are excluded.
Receiving-only Inventory scopeCreate and verify a GRN, confirm received quantities/status and one receipt. QC and stock-entry creation are excluded.
Real upload trafficTechpack creation requests upload URLs, transfers the fixture files and creates the techpack record.
Separate latency budgetsRegular API traffic and techpack requests have different tagged acceptance thresholds.
Durable handoffA local Node coordinator serializes claims and saves a per-run ledger; isolated k6 VUs do not share a mutable JavaScript queue.
No blind write retriesA timeout can hide a committed write. Failed or ambiguous receipts remain recorded for reconciliation.

This is a concurrent-user workload: achieved request throughput depends on application latency, think time and available work. The separate legacy arrival-rate scenario is not the primary role profile described here.

2. Architecture and business journey

Merchandiser workflow

StepBehavior and dependency
1. SessionUse the assigned Merchandiser session; refresh at a safe boundary when required.
2. StyleCreate a unique style and retain its ID.
3. TechpackRequest upload URLs, upload actual fixture files, then create the techpack for that style.
4. SampleCreate a sample and verify its style relationship.
5. BOMRead the created style/combo, create a BOM and verify the linked style.
6. Pre-costingCreate costing for the style; no approval submission.
7. Purchase orderCreate the PO for the same style/combo and verify its relationship.
8. Work orderRead the created PO; derive matching garment sizes, color and quantities; reserve a new number and create the work order.
9. Required approvalUse the existing Senior Merchandiser session to approve the work order, then set SENT_TO_SUPPLIER.
10. HandoffRead back status and style/PO relationships. Only then mark the registered order ready for Inventory.

Approval is a supporting action within Merchandiser VUs. There is no extra approval scenario and no executive login. Multiple Merchandiser VUs can use the shared Senior Merchandiser account; its contention and authorization limits can affect results.

Inventory workflow

StepRequired verification
1. ClaimAtomically claim one ready order from the current run. If none exists, wait and poll again.
2. Read orderConfirm the registered order, style and purchase relationships; require SENT_TO_SUPPLIER.
3. Validate itemsEvery variant must have a positive ordered quantity, a measurement unit and zero previously received quantity.
4. Duplicate guardList GRNs for the work order and require zero existing receipts.
5. ReceiveSend one GRN containing the full ordered quantities for every variant.
6. Verify GRNValidate the returned ID, order relationship, item identities, quantities and units; GET the GRN and validate again.
7. Verify orderPoll safe GETs until the work order is RECEIVED, then check each variant's received quantity.
8. ReconcileRequire exactly one GRN matching the created receipt; mark the claim received in the ledger.

A completed Inventory iteration without a claim is an empty poll, not a completed receipt. Receiving verification proves the receipt and work-order updates; it makes no claim about QC or stock-entry creation.

Claim lifecycle

Ready requires work-order approval and SENT_TO_SUPPLIER. Failures retain claims for reconciliation.

The coordinator listens on loopback and uses a random per-run key. Each transition persists JSON through a temporary file and atomic rename before acknowledgment. Claims do not expire or return to the queue automatically. This prevents local concurrent reassignment; it is not distributed exactly-once delivery or backend idempotency. Process crash recovery/resuming a prior queue is not implemented.

Inventory stays at its allocated concurrency during producer completion grace and drain, then ramps down. Setup, graceful completion, teardown and an open dashboard connection can extend wall time. The smoke command is not expected to end after its 30-second steady phase.

General npm run test:roles defaults to 10 VUs. A manually configured total of 2 outside the smoke command has a 10-minute steady default. ROLE_MERCHANDISER_VUS and ROLE_INVENTORY_VUS can override the allocation, provided their integer sum matches ROLE_TOTAL_VUS and the combined cap remains 50.

4. Think time and realistic pacing

After business actions, the scenario draws a uniform random delay within each range and multiplies it by ROLE_THINK_SCALE. This spreads requests and represents time spent reviewing or entering information. These assumptions require calibration against real usage; they are not recorded production user behavior.

TriggerDefault delayPurpose
First assigned session / refreshed session2–5 secondsNavigation after login. Not a fresh login before every workflow.
Style created15–45 secondsReview style details.
Techpack created20–60 secondsReview uploaded documents. File-transfer time is additional.
Sample created20–60 secondsSample information review.
BOM created30–90 secondsReview material requirements.
Costing created20–60 secondsReview prices and consumption.
Purchase order created15–45 secondsReview order information.
Inventory discovered an eligible order5–20 secondsReview receivable items before receiving.
No ready order / after workflow failure2 secondsPoll/backoff interval; separate from human think time.

The six producer action pauses total 120–360 seconds per workflow, excluding login, API calls, uploads and approvals. Inventory adds 5–20 seconds before receipt, plus any queue wait. Think time affects end-to-end duration and achieved throughput; it is not included in individual HTTP request latency.

Override a range with ROLE_THINK_<STEP>_MIN and ROLE_THINK_<STEP>_MAX, using LOGIN, STYLE, TECHPACK, SAMPLE, BOM, COSTING, PURCHASE or DISCOVER. For example, ROLE_THINK_BOM_MIN=20 ROLE_THINK_BOM_MAX=60. ROLE_THINK_SCALE=0.5 halves human pauses; the smoke command sets it to zero. Queue polling remains enabled.
